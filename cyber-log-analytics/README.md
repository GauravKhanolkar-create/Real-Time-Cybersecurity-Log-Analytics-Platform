# Real-Time Cybersecurity Log Analytics Platform

A reference implementation of a streaming log-analytics pipeline for detecting
security threats (brute-force logins, port scans, large data exfiltration,
blacklisted IPs, and statistical anomalies) in near real time.

```
CSV Dataset / Simulated Producer
        v
   Apache Kafka  (security-logs topic)
        v
Spark Structured Streaming
        v
Rule-based Detection  +  ML Anomaly Scoring (Isolation Forest)
        v
Elasticsearch / MySQL   +   Kafka (security-alerts topic)
        v
Kibana Dashboard        Alert Manager (email / Slack)
```

```
│   └── sample_security_logs.csv

│   ├── log_producer.py         # streams CSV rows into Kafka as live JSON events
│   └── Dockerfile
├── spark_jobs/
│   ├── threat_rules.py         # rule-based detection (brute force, port scan, etc.)
│   └── stream_processor.py     # main Spark Structured Streaming application
├── ml/
│   ├── train_model.py          # offline Isolation Forest training script
│   ├── anomaly_detector.py     # model loading + Spark pandas UDF for scoring

├── storage/

    └── Dockerfile
```

## 1. Prerequisites

- Docker + Docker Compose
- Python 3.10+ (for local scripts / training)

## 2. Generate the sample dataset (already included, regenerate if needed)

```bash
cd data
python3 generate_sample_logs.py
```

This produces `sample_security_logs.csv`: a mix of normal traffic plus
labeled brute-force, port-scan, large-transfer, and blacklisted-IP incidents,
used both as the ML training set and as the producer's replay source.

## 3. Train the anomaly detection model

```bash
pip install -r requirements.txt
python3 ml/train_model.py --csv data/sample_security_logs.csv
```

> **Note:** `requirements.txt` intentionally does **not** include a MySQL
> Python driver, since none of the Python scripts in this project connect
> to MySQL directly (Spark writes to it via its own JDBC driver inside
> `stream_processor.py`, and the schema loads automatically from
> `storage/init_mysql.sql`). If you later write a script that needs direct
> MySQL access from Python, see `requirements-mysql-optional.txt`.

This fits a `StandardScaler` + `IsolationForest` on the numeric features
(bytes sent/received, duration, destination port, rolling failed-login and
port-fanout counters) and saves both to `ml/models/`.

## 4. Bring up the infrastructure

```bash
docker compose up -d zookeeper kafka kafka-init-topics elasticsearch kibana mysql spark spark-worker
```

> **Note:** The `spark`/`spark-worker` services build a small custom image
> (`spark/Dockerfile`) on top of `apache/spark:3.5.1` that adds the Python
> packages `stream_processor.py` needs at runtime (`pyyaml`, `pandas`,
> `numpy`, `scikit-learn`, `joblib`) — the bare official image only ships
> Python + PySpark. The first `docker compose up` will build this image
> (a minute or two); afterward it's cached and reused instantly. If you
> ever change `spark/requirements-spark.txt`, rebuild with
> `docker compose build spark spark-worker`.

Check that Kafka topics were created:

```bash
docker exec kafka kafka-topics --bootstrap-server kafka:9092 --list
```

Check that the MySQL schema loaded correctly:

```bash
docker exec -it mysql mysql -u cyberlog -pcyberlog_pw cyberlog_db -e "SHOW TABLES;"
```

Create the Elasticsearch indices with proper mappings:

```bash
pip install elasticsearch
ELASTICSEARCH_HOST=http://localhost:9200 python3 storage/es_writer.py
```

## 5. Start the log producer (simulated live traffic)

```bash
docker compose up -d producer
docker compose logs -f producer
```

Or run it locally against the Dockerized Kafka:

```bash
KAFKA_BOOTSTRAP_SERVERS=localhost:29092 python3 producer/log_producer.py
```

## 6. Run the Spark Structured Streaming job

From inside the Spark container (recommended, since it already has PySpark
and can reach the other services by container name):

```bash
docker exec -it spark /opt/spark/bin/spark-submit \
  --packages org.apache.spark:spark-sql-kafka-0-10_2.12:3.5.1,com.mysql:mysql-connector-j:8.4.0 \
  /opt/app/spark_jobs/stream_processor.py
```

> **Note:** This project uses the official `apache/spark:3.5.1` image
> (not Bitnami's) since Bitnami discontinued free public access to their
> container images on Docker Hub in 2025 — `bitnami/spark` and similar
> tags now require a paid Bitnami Secure Images subscription. The
> `spark`/`spark-worker` services in `docker-compose.yml` start the
> standalone Master/Worker directly via `spark-class` rather than the
> `SPARK_MODE` environment variable Bitnami's image used to support.

The job will:
- print enriched, scored events to the console
- write every enriched event into the MySQL `security_logs` table (via `foreachBatch` + JDBC)
- publish any `high`/`critical` severity events to the `security-alerts` Kafka topic

Uncomment the Elasticsearch sink block in `stream_processor.py` (and add the
`elasticsearch-spark` connector to `--packages`) once you want events
persisted to Elasticsearch for Kibana dashboards too.

## 7. Start the alert manager

```bash
docker compose up -d alert-manager
docker compose logs -f alert-manager
```

Configure `SMTP_*` / `SLACK_WEBHOOK_URL` environment variables in
`docker-compose.yml` (or a `.env` file) to enable real email/Slack delivery;
otherwise alerts are just printed to the console.

## 8. Explore in Kibana / query MySQL

- Kibana: http://localhost:5601 — create an index pattern on `security-logs*`
  or `security-alerts*` once the ES sink is enabled.
- MySQL:
  ```bash
  docker exec -it mysql mysql -u cyberlog -pcyberlog_pw cyberlog_db
  ```
  then, e.g.:
  ```sql
  SELECT final_severity, COUNT(*) FROM security_logs GROUP BY final_severity;
  SELECT * FROM security_logs ORDER BY event_time DESC LIMIT 20;
  ```

> **Note:** The MySQL container exposes its port to the host as **3307**
> (not the default 3306), to avoid conflicting with a MySQL server you
> may already have running locally. This only affects connections *from
> your host machine* (e.g. MySQL Workbench, DBeaver, or a local script) —
> use `localhost:3307` for those. Containers talking to each other over
> the Docker network (like the Spark job) still use `mysql:3306`
> internally, which is unaffected and requires no configuration change.

## Detection logic summary

| Rule                | Trigger                                                        | Severity |
|---------------------|-----------------------------------------------------------------|----------|
| Brute-force login    | >= N failed logins from the same source within a rolling window | high     |
| Port scan            | >= N unique destination ports contacted within a rolling window | high     |
| Blacklisted IP        | Source IP matches a configured blacklist                        | critical |
| Large data transfer  | bytes_sent + bytes_received exceeds a configured threshold      | medium   |
| ML anomaly (Isolation Forest) | Anomaly score above configured threshold                | high (if above threshold) |

All thresholds live in `config/config.yaml` under the `detection` key.

## Notes on this reference implementation

- The producer ships pre-computed rolling counters
  (`failed_login_count_5m`, `unique_ports_contacted_1m`) for simplicity.
  In a production deployment, compute these directly in Spark via stateful
  windowed aggregations (`groupBy(window(...), src_ip)`) joined back onto
  the raw event stream — a starting point for that is sketched in
  `spark_jobs/stream_processor.py::enrich_with_rolling_features`.
- The ML model is a simple unsupervised Isolation Forest chosen for clarity;
  swap in a supervised classifier (e.g. `RandomForestClassifier` /
  Spark MLlib `GBTClassifier`) if you have labeled incident data and want
  precision/recall tuning instead of a pure anomaly score.
- MySQL has no native array type, so the `triggered_rules` column (a list
  of rule names like `["BRUTE_FORCE_LOGIN", "PORT_SCAN"]`) is stored as a
  `JSON` column instead. Query it with MySQL's `JSON_CONTAINS()` /
  `JSON_TABLE()` functions if you need to filter on individual rule values.
- This project is intended for learning/demo purposes with synthetic data.
  Before pointing it at real production logs, review authentication,
  network exposure (don't expose Kafka/ES/Kibana/MySQL ports publicly),
  and data retention/privacy requirements for your environment.
